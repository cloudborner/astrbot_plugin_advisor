# 推荐评分规范

总分固定为 100 分，任何大模型都不能修改权重或直接给总分。

| 维度 | 满分 | 规则摘要 |
| --- | ---: | --- |
| 群聊需求匹配 | 30 | 用户确认后的模型需求与市场描述/标签进行可解释匹配；证据不足时降低得分。 |
| 市场使用情况 | 20 | 累计下载 12 分（60%），Stars 8 分（40%）。 |
| 平台/版本兼容 | 20 | 平台声明最多 12 分，AstrBot PEP 440 版本满足最多 8 分。明确不兼容时该项为 0。 |
| 服务器资源适配 | 15 | 根据空闲/峰值内存与 CPU、磁盘、网络、当前可用资源及证据置信度扣分。 |
| 维护活跃度 | 10 | 市场更新时间 ≤90/180/365/730 天分别得 10/8/6/3，超过 730 天得 1。 |
| 部署复杂度 | 5 | 外部进程、后台任务、高磁盘风险及已安装插件容量冲突扣分。 |

## 市场分

对市场中每个插件分别计算：

```text
d = log1p(download_count)
s = log1p(stars)
market_usage = 12 * lower_percentile(d) + 8 * lower_percentile(s)
```

`lower_percentile(x) = count(value < x) / (N - 1)`。相同数值使用同一排名；零下载/零 Star 不会因为大量并列而获得高分。`N=1` 时使用中性 0.5。

## 需求分

需求分析以用户确认后的去身份化连续聊天为依据。模型只能给出需求、能力检索词和真实证据编号，
不能选择插件或决定分数。候选插件只有在名称、简介、标签或市场分类中命中相同能力时才获得
对应需求分，并在报告中列出匹配原因。旧版媒体、命令、搜索等计数只作为内部有界行为特征，
不得作为“聚合需求计数”展示给用户，也不能在缺少聊天证据时创造主题。

短 ASCII 别名（如 `rm`、`ai`）必须满足字母数字边界，避免 `email`、`daily` 一类子串误判。
同一段文字被关键词和正则同时命中时合并计数，单条消息的重复也不能绕过“至少多条消息出现”
的持久化隐私阈值。

## 兼容性硬限制

- 市场明确声明不支持当前适配器：兼容分 0，总分最高 39。
- 当前 AstrBot 版本不满足插件 PEP 440 约束：兼容分 0，总分最高 39。
- 声明缺失时不给满分，并提示需要人工复核。

## 资源和冲突

服务器探针优先读取 cgroup 限额/占用，再结合 `/proc/meminfo`。内存至少预留
`max(384 MiB, 总内存的 30%)`。高峰值画像在余量不足时额外扣分；高磁盘、
高网络和空闲 CPU 风险也会在 15 分资源项内扣分。置信度低于 0.65 时保守扣分，
避免“没有证据”被当成“确定轻量”。

冲突检测只报告可证明的容量叠加：

- 小于 4 GiB 的服务器同时存在多个 L3/L4 峰值内存画像；
- 候选与已安装插件都需要 Chromium/FFmpeg 等高负载外部进程；
- ≤2 核 CPU 上叠加多个可能的后台任务。

共享普通依赖不等于冲突；静态信息不足时不宣称语义不兼容。

## 置信度

- GitHub Tree + SBOM：基准 0.72。
- 只有 GitHub Tree：基准 0.52。
- 只有市场元数据：基准 0.28。
- 没有命中任何已知特征时，上限 0.38。
- 大模型回退的置信度上限 0.70，且只能提高风险、不能降低确定性风险。
